# 数字分词对算术能力的影响：对比实验

配套脚本：`math/eval_math_digits.py`。承接 [tokenizer_digits.md](./tokenizer_digits.md) 的改动。

## 实验设计

因为本地没有预训练权重，无法直接测「patch 后的 tokenizer + 已有模型」，所以改用一个更干净的方式：**用合成算术数据从零训练两个只有 tokenizer 不同的小模型**。

严格控制的变量：

- 同一份 `model/` 词表复制两份，只改 `pre_tokenizer`（`ByteLevel` vs `Sequence[Digits, ByteLevel]`），vocab / merges 完全相同
- 同样的题目（同一 `data_seed` 生成）、同样的参数量（1.71M，hidden 128 / 4 层）、同样的训练步数、同样的 `train_seed`、同样的优化器与学习率调度
- 测试集先抽取，训练集生成时排除掉所有测试题面，**零泄漏**
- 只对答案段计损失，题面部分置 `-100`
- 评测用贪心解码（无采样随机性），按整数值判定对错

两个指标：

- **完全正确率** — 答案字符串完全一致
- **逐位命中率** — 右对齐逐位比较，衡量「接近程度」而非全对全错

## 结果

### 三位数加法（`0-999`，20000 训练题 / 500 测试题，4000 steps）

| 组 | 完全正确率 | 逐位命中率 | 平均序列长度 |
|---|---|---|---|
| 原始 ByteLevel | 5.8% | 60.1% | 10.2 tokens |
| Digits + ByteLevel | **90.4%** | **95.1%** | 12.3 tokens |
| 差值 | **+84.6%** | +35.0% | +21% |

换种子复现（`train_seed 7` / `data_seed 99`）：

| 组 | 完全正确率 | 逐位命中率 |
|---|---|---|
| 原始 ByteLevel | 41.0% | 79.8% |
| Digits + ByteLevel | **88.2%** | **94.5%** |
| 差值 | **+47.2%** | +14.6% |

### 两位数乘法（`0-99`，9000 训练题 / 500 测试题，4000 steps）

| 组 | 完全正确率 | 逐位命中率 |
|---|---|---|
| 原始 ByteLevel | 34.0% | 74.2% |
| Digits + ByteLevel | **44.4%** | **80.8%** |
| 差值 | **+10.4%** | +6.6% |

## 关键观察

### 1. 加法这组的变量极其干净

两组的**题面切分完全相同**，都是 `9|8|9|+|7|9|6|=`。唯一差别在答案侧：

```
对照组答案:  17 | 8 | 5      ← 首两位被合并成一个 token
实验组答案:  1 | 7 | 8 | 5
```

差别只在答案的第一个 token，正确率就从 5.8% 拉到 90.4%。原因是对照组要在**同一个 token 里同时预测千位和百位**，这两位的进位来源完全不同（千位只取决于是否进位，百位取决于十位进位），却被迫压进一次预测。

### 2. 训练 loss 差了一个数量级

```
对照组:  step 1000  loss 1.4745  →  step 4000  loss 0.9375
实验组:  step 1000  loss 0.2161  →  step 4000  loss 0.0563
```

对照组的 loss 在 0.94 附近就下不去了。这不是训练不充分，而是任务在那套切分下本身更难拟合。

### 3. 错的方式很说明问题

对照组的错误集中在**低位**，高位反而常常是对的：

```
✗ 989+796=1788   (正确 1785)     末位错
✗ 961+826=1788   (正确 1787)     末位错
✗ 663+638=1296   (正确 1301)     进位错
✗ 527+592=1110   (正确 1119)     末位错
```

60.1% 的逐位命中率配 5.8% 的完全正确率，说明模型学到了大致量级，但精确的进位链没学会。而乘法组的对照组错误同样是低位偏差（`12*98=1156` vs `1176`、`82*79=6438` vs `6478`）。

### 4. 对照组方差很大，实验组稳定

两次种子下，对照组 5.8% → 41.0%（波动 35 个百分点），实验组 90.4% → 88.2%（波动 2 个百分点）。

多位数字 token 的切分依赖具体数值（`17|8|5` 还是 `1|78|5` 取决于词表里恰好有哪些 merge），所以对照组的表现严重依赖训练数据里数值的分布是否碰巧对齐。这种不稳定本身就是问题——**它意味着模型的数学能力对数据分布过敏**。

### 5. 代价是序列变长

加法组平均序列长度 10.2 → 12.3 tokens（+21%）。在算术任务上这个代价明显值得；但如果语料数字密度高，需要留意 `max_seq_len` 的占用。

## 复现

```bash
cd math

# 加法（主结论）
python eval_math_digits.py --task add --steps 4000 --n_train 20000 --n_test 500

# 乘法
python eval_math_digits.py --task mul --lo 0 --hi 99 --steps 4000 --n_train 9000

# 换种子验证稳定性
python eval_math_digits.py --task add --steps 4000 --train_seed 7 --data_seed 99
```

在 M 系列 Mac 的 MPS 上每组约 80 秒，一次对比实验约 3 分钟。也支持 `--task sub`、`--device cpu/cuda`。

## 这个实验能说明什么、不能说明什么

**能说明**：在其他条件严格相同的情况下，多位数字 token 确实是算术能力的瓶颈，而不只是理论上的顾虑。方向在三组实验、两个不同种子下一致。

**不能说明**：
- 这是 1.71M 的小模型 + 纯算术合成数据，绝对数值不能外推到 64M 的 minimind 在自然语料上的表现
- 真实收益还取决于继续预训练的充分程度（见 `tokenizer_digits.md` 的权重说明）
- 只测了整数四则运算，没有覆盖小数、科学计数法、日期、单位换算等场景
