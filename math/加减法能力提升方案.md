# MiniMind 加减法能力方案

> 状态：**v5 已训练完成并通过评测，总体准确率 99.5%（2500 题）**
> 基线模型：`out/full_sft_768.pth`（hidden_size=768, layers=8, 63.9M 参数）
> 当前权重：`out/full_sft_math_v5_768.pth`

---

## 1. 背景：为什么需要专门的课程数据

基线 `full_sft` 的加减法**几乎完全不可用**，且不是"效果不佳"：

| 位数 | 加法 | 减法 |
|---|---|---|
| 1 位 | 24% | 12% |
| 2 位及以上 | **0%** | **0%** |

典型输出是 `45+76 → 456`（直接拼接）、`9-3 → 1.618`。CoT 提示、thinking
模式都是 0/12 —— **这是能力缺失，不是引导不足**。

四个根因：

1. **Tokenizer 把数字切成与数位无关的块。** 6400 词表的 BPE 按频率贪心合并：
   `123` 是 1 个 token，`431` 是 2 个，`1000` 切成 `['1','000']`。模型没有
   "个位/十位"这个可寻址的概念。主流模型要么一位一 token（LLaMA、Gemma），
   要么定长分组（GPT-4、Llama 3），关键不在分不分组，而在**规则是否固定**。
   MiniMind 属于"分组但规则随机"，比不分组更糟。

2. **算术在原数据里是副产品。** SFT 中 2.65% 的行含算式，83% 集中在 1–2 位，
   4 位以上仅 559 条。模型只能记住高频小数组合。

3. **原数据含错误算式。** SFT 算式自洽率 93.1%，等于主动灌噪声。

4. **直答格式要求常数深度算完进位链。** 8 层 / 768 维的串行计算深度有限，
   4 位加法的进位传播在没有中间 token 当草稿纸时**理论上就做不到**。

Tokenizer 已冻结（pretrain 用它跑过，改词表需重跑预训练），所以**全部修复
都在数据层**。

## 2. 格式设计

### 2.1 数字表示：一位一 token

算术场景的数字一律空格分隔，利用词表里带前导空格的单字符 token：

```
'6 8 5' → ['6'] [' 8'] [' 5']    # 每个数字独占一个 token，完全对齐
```

### 2.2 演算顺序：低位优先

按「个位 → 高位」逐步展开，先输出逆序结果，再输出正序答案：

```
竖式计算 4 3 1 + 2 5 4
个位: 1 + 4 = 5，写 5 进位 0
十位: 3 + 5 = 8，写 8 进位 0
百位: 4 + 2 = 6，写 6 进位 0
逆序: 5 8 6
答案: 6 8 5
```

- 每一步只需读「当前两位 + 上一步进位」，**全部在已生成的 token 里**
- 进位天然从低位向高位传播，模型只学一个固定的局部规则
- `逆序` 行与演算顺序一致（纯拼接），`答案` 行是它的反转（纯拷贝）

**没有自然语言结论行**（`所以 431 + 254 = 685`）。它对正确性零贡献
（`parse_answer` 优先读 `答案:` 行），却要求模型把结果再正序抄一遍 ——
实测 1850 题里 46 例「答案行≠结论行」，其中 39 例是答案行对、结论行抄错。
多一次拷贝就多一次出错机会。删掉后序列还短了约 10%。

### 2.3 符号判断必须有显式演算

减法开头插入逐位比较（`compare_trace`）：

```
先比较 2 7 和 2 6 的大小
位数相同，都是 2 位，从最高位逐位比较
十位: 2 = 2，相同，继续比下一位
个位: 7 > 6，分出大小，所以 27 更大
竖式计算 2 7 - 2 6
```

**这一步不能省。** 若只写"a 小于 b"这句结论，模型得在单次前向里猜出谁大，
实测 `b/a>0.95` 时准确率仅 **19%** —— 它学到的是"按首位数字猜大小"，首位
相同就掷硬币。拆成"先比位数、再从高位逐位比"之后，每步只需比较两个一位数。

### 2.4 不等长操作数天然支持

低位对齐后短操作数补 0（`math_format.py:63`）：

```python
x = da[i] if i < len(da) else 0
y = db[i] if i < len(db) else 0
```

**这是低位优先的直接红利**：从高位算需要先知道长度差才能对齐；从低位算，
个位永远对个位，不等长与等长走完全相同的代码路径。`1000000 + 7` 同样正确。

## 3. 数据生成

程序化生成，保证 100% 正确（彻底避开原数据 7% 的噪声）。位数**均匀采样**
1–8 位，而非像自然数据那样集中在 1–2 位。

### 3.1 采样分支

每个分支都对应一个实测过的失败模式，不是凭空配比（30 万样本插桩统计）：

| 分支 | 标称 | 实测 | 针对的失败 |
|---|---|---|---|
| `sample_pair`（通用） | 63% | 62.90% | 位数均匀 + 内含进位/位数差/含 0 三类难例 |
| `sample_close_pair` | 12% | 12.08% | `b/a > 0.9` 符号难判区（见 §2.3） |
| `sample_repdigit_pair` | 8% | 7.98% | `999+99` 全同数字，两侧全同 80% |
| `sample_longrun_answer_pair` | 6% | 5.95% | 答案带长重复串，操作数普通 |
| `sample_negative_pair` | 5% | 5.02% | 负数结果，共享后缀 50% |
| `sample_equal_pair` | 3% | 3.05% | `a - a`，前导零全塌缩 |
| `sample_zerorun_pair` | 3% | 3.01% | `2222-222`，反转拷贝数不清 0 |

`sample_pair` 内部再分：连续进位/借位 15%、位数差 ≥2 10%、含 0 操作数 8%、
其余位数均匀。

各分支为什么存在，见 §6「失败模式档案」。

### 3.2 场景覆盖率（实测，30 万样本，`--max_digits 8`）

**分支占比 ≠ 场景覆盖。** 分支会被后续环节（问法模板、`neg_ratio` 条件
概率、`a>=b` 交换）继续稀释，必须按语义维度单独量：

| 场景 | 覆盖率 | | 场景 | 覆盖率 |
|---|---|---|---|---|
| 不等长 | 58.82% | | 答案零串 ≥3 | 8.62% |
| 操作数含 0 | 47.06% | | 连续进位 ≥5 | 7.47% |
| 答案长串 ≥3 | 21.22% | | 结果为负 | 7.27% |
| 连续进位 ≥3 | 18.69% | | 操作数是 0 | 6.44% |
| 短数在前 | 18.40% | | 答案零串 ≥4 | 6.35% |
| 位数差 ≥3 | 16.34% | | 负数·不等长 | 4.00% |
| 需去前导零 | 16.15% | | 结果为 0 | 3.70% |
| 答案长串 ≥4 | 14.54% | | **连续借位 ≥5** | **3.63%** |
| 连续借位 ≥3 | 13.01% | | 负数·等长 | 3.26% |
| a 全同数字 | 12.48% | | 负数·共享后缀 | 2.11% |
| 等长且首位相同 | 11.88% | | 需去 ≥3 个前导零 | 2.26% |
| 等长且 b/a>0.95 | 11.27% | | **负数·等长且接近** | **0.23%** |
| 两侧全同 | 8.67% | | **需去 ≥5 个前导零** | **0.83%** |
| 答案长串 ≥5 | 8.65% | | | |

加粗的四项是**已知偏低项**，处理建议见 §7。

**减法「短在前」只占 8.9%**（加法 28.2%）是设计使然：减法短在前必然得负数，
由 `sample_negative_pair` 统一控制，不是漏洞。

**操作数顺序随机交换**：各采样分支一律"位数多的在前"，若不交换，`4 + 804`
这类写法是 0% 覆盖。

### 3.3 问法与运算符

11 种算式模板（8 种带空格 + 3 种紧凑，如 `99+999`）+ 3 种口语模板。
实测占比：**带空格 48.5%、紧凑 29.4%、口语 22.2%**。15% 概率带 system prompt。

紧凑写法必须单独覆盖：BPE 对两种写法的切分完全不同，`999` 在 `99+999` 里是
`['99','9']`，在 `99 + 999` 里是 `[' 9','99']` —— 只训带空格的话，模型面对
紧凑写法时看到的 token 序列与训练时**没有任何重叠**。

运算符实测 **减 55.5% / 加 44.5%** —— 三个 `force_op='-'` 的分档把减法抬高了，
符合预期（减法本就更难）。

## 4. 文件与命令

| 文件 | 作用 |
|---|---|
| `scripts/math_format.py` | 轨迹生成 + 答案解析（生成与评测**共用同一份**） |
| `scripts/gen_math_data.py` | 课程数据生成器 |
| `scripts/eval_math.py` | 按「位数 × 运算符 × 写法」十档评测，2500 题 |

> **为什么生成和解析共用一个模块**：曾经正确输出 `答案: 6 8 5` 被"取最后一个
> 数字"的提取逻辑判成 5，导致 55% 的真实准确率被误报为 0%。格式定义必须单点维护。

### 4.1 生成数据（CPU，约 2–3 分钟）

```bash
python scripts/gen_math_data.py \
  --out dataset/math_addsub_v5.jsonl \
  --n 400000 \
  --max_digits 8 \
  --mix_general dataset/sft_t2t_mini.jsonl \
  --mix_ratio 0.3
```

产出约 57 万条（40 万数学 + 17 万通用）。

### 4.2 单卡训练

```bash
cd trainer && python train_full_sft.py \
  --data_path ../dataset/math_addsub_v5.jsonl \
  --from_weight full_sft \
  --save_weight full_sft_math_v5 \
  --epochs 1 \
  --batch_size 32 \
  --learning_rate 2e-5 \
  --max_seq_len 512 \
  --dtype bfloat16 \
  --num_workers 8 \
  --from_resume 1
```

### 4.3 评测

```bash
python scripts/eval_math.py --weight full_sft_math_v5 --max_digits 8 --n 25
python eval_llm.py --weight full_sft_math_v5      # 通用能力是否退化
```

### 4.4 关键参数

| 参数 | 取值 | 原因 |
|---|---|---|
| `--max_seq_len` | **512** | 实测 median=198、p95=357、max=434 token，超 512 占比 0%。默认 768 会白烧 40% 算力 |
| `--mix_ratio` | 0.3 | 混 30% 通用数据防灾难性遗忘，实测无退化 |
| `--from_weight` | full_sft | 基于已有 SFT 权重继续训，非从头开始 |
| `--batch_size` | 32 | 24G 显存的保守值。显存充足可上 64 并把 lr 提到 3e-5 |
| `--from_resume` | 1 | 单卡长跑建议开启 |

> **必须从 `full_sft` 重训，不要在旧的 math 权重上增量。** 每一版都会把某条
> 伪规律内化（曾出现过"第一个操作数更长"、全同数字的位数），增量训练容易残留。
> 且当前格式（无结论行）与早期 checkpoint 不兼容。

## 6. 失败模式档案

每一条都是实测出来的，记录**机制**而非现象 —— 生成器和评测器的每个分档
都能在这里找到对应的来源。标 ⚠️ 的是 v5 仍未解决的。

### 6.1 ⚠️ 交换分支没触发，借位跑出 10 的补码（v5 主要残留）

`负数` 档 96.6%，是唯一明显掉队的档位。6 个错例里 4 个**精确命中**同一机制：
模型没有执行 `a<b → 交换 → 取负`，而是直接对 `小 - 大` 跑借位循环，最高位
的借位无处可借被丢弃，结果正好是 10 的补码。

| 题 | 真值 | 预测 | `10ⁿ − \|真值\|` |
|---|---|---|---|
| `15-17` | -2 | **98** | 98 ✅ |
| `14-15` | -1 | **99** | 99 ✅ |
| `382-393` | -11 | **989** | 989 ✅ |
| `77583099-78524249` | -941150 | **99058850** | 99058850 ✅ |

`257-179 = 78` 答成 `-922` 是同一机制的镜像：比较行判反（以为 257 < 179），
于是说"结果为负，先计算 179 - 257"，再对这个 `小-大` 跑借位得 922，补上负号。
**`a>b` 时也会发作** —— 这一例落在`紧凑`档，不在负数档。

**触发条件是等长且接近。** 6 个负数错例全部等长（`14-15` 差 1、
`77583099-78524249` 8 位数差 6 位）。而共享后缀形状（`99-199`）已达 99.4%。

覆盖率实测：

| | 训练 | 评测 | 倍率 |
|---|---|---|---|
| 负数·不等长 | 4.00% | 54% | |
| 负数·等长 | 3.26% | 46% | |
| **负数·等长且接近**（差值比操作数短 ≥2 位） | **0.23%** | **3%** | **12×** |

`sample_negative_pair` 里等长档占 30%，但档内 `randint(lo, b-1)` 是**均匀**
取 `a`，绝大多数采出来的两数差得很远（首位就分出大小），真正需要比到末几位
的样本被稀释到 0.23%。

### 6.2 ⚠️ 前导零去过头

`14691927 - 14691816 = 111` 答成 **0**。竖式跑 8 位得 `00000111`，要一次性
去掉 5 个前导零，模型把 `111` 也一起吃掉了。

这是 §6.5「写长串数不清」的**反面动作**。实测覆盖：需去 ≥5 个前导零只有
**0.83%**，≥3 个 2.26%。`sample_equal_pair` 只造"全塌缩成 0"（k = n-1）这个
极端，中间的 k=3~6 没有分支覆盖。

### 6.3 长重复串数不清位数

**根因是计数，不是 tokenizer。** 曾长期把它归给 BPE 的紧凑写法切分，这是
错的，两条证据推翻：

- 带空格的 `2222 - 222` 同样错（答 200）
- 6400 词表里两位重复 token 只有 `00 11 22 33 99` 五个，数字 4~8 在紧凑
  写法下**本来就是一位一 token**（`66666-6666` → 10 个单字符 token），
  位数信息完整 —— 照样答成 `600060`

tokenizer 只在 1/2/3/9 上额外添了一刀。所以 `sample_repdigit_pair` 不偏向
任何数字，写法也按一半一半（紧凑/带空格），两类诱因都要练到。

两侧都全同是最难的（`444-222`、`333333+999999`），故给 80% 权重。

**v5 已解决**：全同数字 100%、长零串 100%。

### 6.4 位数计数错误投影到符号判断

`99-199` 答成 800（v4）：模型在比较行把 `99` 的位数报成 3 位，走进
"位数相同→逐位比较"分支，结论反了（"所以 99 更大"），**整个丢掉负号**，
后面竖式又按 `a>=b` 算。而 `77-777`（不共享后缀）同时是对的。

分界线是 `b` 的末尾是否恰好等于 `a`（`199` 的后两位就是 `99`）—— 两个数字串
共享后缀、只差最前面一位时最难区分。

**v5 已解决**：负数共后缀 99.4%（该形状覆盖从 0.020% 提到 2.11%）。

### 6.5 反转拷贝的终止判断是高熵区

`44444 - 4444` 答成 `4000` / `40005`（两次采样两种错法）：竖式 5 步全对、
逆序行对，只错在最后一步反转拷贝的第 5 位。

答案行 token 序列是 `['答案', ':', ' 4', ' 0', ' 0', ' 0', ' 0']` —— 后四个
完全相同，模型写完第 4 个要决定"再写一个还是停"。统计训练数据里
「已写 k 个连续 0，下一步继续还是终止」：

| k | 继续 | 终止 | P(继续) |
|---|---|---|---|
| 1 | 3932 | 20294 | 16.2% |
| 2 | 1854 | 2078 | 47.2% |
| 3 | 1188 | 666 | **64.1%** |
| 4 | 638 | 550 | **53.7%** |
| 5 | 61 | 577 | 9.6% |

**k=2/3/4 是高熵区，k=4 几乎是掷硬币**，而 `40000` 正好卡在 k=4。三个因素
叠加在末位：答案行末位对应逆序行**首位**（相隔约 10 个 token，反转拷贝
越往后回看距离越远）；没有终止锚点（末位错了直接定死）；`eval_llm.py` 用
temperature 0.85 采样会放大错误（`eval_math.py` 是贪心，同题可能就对了）。

**v5 通过数据层压住了**（答案零串 ≥4 覆盖 2.00% → 6.35%，长零串档 100%）。
但这是缓解不是结构性修复 —— `逆序 → 答案` 仍是纯反转，没有任何显式的长度状态。

### 6.6 已解决且未复发的早期缺陷

| 缺陷 | 现象 | 修复 | 现状 |
|---|---|---|---|
| 短数在前 0% 覆盖 | `4 + 804 → 908`（学到"第一个操作数更长"的伪规律） | 各采样分支内随机交换顺序 | 99.3% |
| 紧凑写法 0% 覆盖 | `211+226 → 4327`（token 序列与训练无重叠） | 新增 3 个紧凑模板，占比 29.4% | 99.4% |
| 符号判断无演算 | `27-26 → -999`，`b/a>0.95` 时仅 19% | `compare_trace` 逐位比较 + `sample_close_pair` | 等长 100% |
| 结果恰为 0 | `7777-7777 → 70` | `sample_equal_pair` | 见 §6.2（相邻缺陷仍在） |
| 紧凑不等长 | `99+999` 抄成竖式 `9 9 + 9 9 9 9` | 评测单独成档 + 生成器覆盖 | 100% |

### 6.7 无共同机制的偶发错例

`54202347-461980` 错 1 位、`2220+387162` 错末两位、`73450569+45455481` 错中段
3 位、`98561653+53130` 错高位 4 位。分散在不同位置、不同运算符，8 位居多。

属于长链演算的偶发失误。**25 题/档的粒度下 1 题就是 4%，不足以支撑归因** ——
要判断是否真实缺陷，需把 `--n` 提到 100 单跑 8 位档看是否复现。

## 7. 下一步（按性价比排序）

### 7.1 补等长接近负数（主修，性价比最高）

`sample_negative_pair` 等长档内部让 `a` 贴着 `b` 取（共享高位前缀、只在末几位
分出大小），把覆盖从 0.23% 提到 2% 量级。

**同时必须改评测器**：`neg` 档按"接近程度"分桶，否则改完照样看不见
（§8 检查 6 的老坑）。

### 7.2 补中间深度的前导零

`sample_equal_pair` 扩成"需去掉 k 个前导零"，k 在 1~n-1 均匀，补上 §6.2 的
k=3~6 空档。

### 7.3 连续借位 ≥5（仅 3.63%，暂不处理）

进位 ≥5 有 7.47%，是它的两倍。原因是 `sample_pair` 的难例分支造
`1000…0 - 小数` 时 `b` 最多 4 位，`b` 一大借位链就断。
**不在任何一轮的实测失败清单里**，故未处理；若出现长借位错例，
在 `sample_pair` 加一条 `10^d - (10^k-1)` 即可。

### 7.4 结构性修复（要改格式重训，暂不做）

§7.1 和 §7.2 都只是"补档"，而机制在**"交换分支要不要触发"这个决策**上，
不在操作数长相上 —— 补数据只是让那个决策点见得更多，未必是结构性修复。

真正结构性的做法：在 `compare_trace` 之后、竖式之前插一行显式状态
`a < b，交换后计算 b - a`，让"已经交换过"成为可寻址的 token 而非隐式状态。
同理 §6.5 可以给答案行加位数锚点（`答案(5位): 4 0 0 0 0`）。

两者都要改格式 + 重训一轮，且当前准确率已 99.5%，**建议先做 §7.1/§7.2 看
能否用数据层解决**。

## 8. 方法论：十二轮排查，没有一次是"模型能力不足"

| 轮次 | 性质 | 盲区 | 后果 |
|---|---|---|---|
| 1 | 评测盲区 | 答案提取逻辑与输出格式不匹配 | 真实 55% 被误报为 0% |
| 2 | 评测盲区 | 评测集只有等长操作数 | 不等长 25% 的短板不可见 |
| 3 | 评测盲区 | 只有带空格写法、只有长数在前 | 看似 100%，实际两档接近 0% |
| 4 | 格式设计缺陷 | 符号判断没有演算过程 | 等长减法 91%，`b/a>0.95` 时仅 19% |
| 5 | 采样分布盲区 | 维度有专档，但极低概率子区从未抽中 | `99+999` 稳定读错题 |
| 6 | 采样分布盲区 | 结果恰为 0 占比仅 0.75% | `7777-7777` 答成 70 |
| 7 | 训练/评测分布不一致 | 档位两边都有，但子分布不同（训 3.39% vs 测 100%） | 全同数字档卡在 94.9% 不动 |
| 8 | 采样分布盲区 | 结果里长重复串（≥4 连续段仅 7.5%） | `2222-222` 答成 0 |
| 9 | **归因错误** | 把位数读错全归给 tokenizer，据此把预算压给紧凑写法 | 带空格档覆盖只剩 1.6%，而它同样会错 |
| 10 | 评测盲区 + 稀释链 | 评测集 2000 题里负数结果 **0 题**；`neg_ratio` 是条件概率，名义 12% 实际 2.8% | 报 99.0%，`99-199` 答成 800 |
| 11 | **采样打偏** | 补了 zerorun 档，但复刻的是错例的操作数长相，机制却在答案侧 | 答案零串 ≥4 只从 2.00% 抬到 3.33% |
| 12 | **档内分布盲区** | 负数档整体 7.27% 达标，档内"等长且接近"只有 0.23% | v5 负数档 96.6%，6 个错例全是这一形状 |

四类性质：

**评测盲区（1、2、3、10）**——评测覆盖不到的维度，训练数据里必然也是 0% 覆盖，
两者都源自同一份对"问题空间"的假设。第 10 轮最严重：每一档都写了
`if op == '-' and b > a: a, b = b, a`，2000 题里负数一题不剩，分数报到 99.0%
也毫无意义。**九轮之后仍然踩同一个坑。**

**格式设计缺陷（4）**——方案核心是"把多步计算拆成逐 token 演算"，但符号判断
被漏掉了，仍要求单次前向直接出结论。§6.5 的"还剩几位"是同一类问题。

**采样分布盲区（5、6、8、11、12）**——最隐蔽的一类，且**会一直复发**：
第 5/6/8 轮是"档位压根没有"；第 11 轮是"补了档但形状打偏"（复刻了错例的
操作数长相，机制却在答案侧）；第 12 轮是"档位和比例都对，但档内分布是均匀的"。
**分档的粒度决定了能看见什么；档内的分布决定了看不见什么。**

**归因错误（9）**——性质与其余都不同：其余是"没看见"，这轮是"看见了但解释错了"。
"位数读错源于 tokenizer"四轮里没人质疑，还据此把 repdigit 预算的 70% 压给紧凑。
**错误的归因比没有归因更危险** —— 它指挥你把资源投到错的地方，且因为局部有效
（紧凑档确实涨了），不容易被发现。

### 通用检查清单

1. **每个"结论性断言"都要有对应的演算过程。** 凡是模型必须一次性猜出来的量
   （谁大、几位数、要不要进位、还剩几位），都是失败点。
2. **每个档位内部按难度分桶再看一遍。** 按 `b/a` 比值、按数字重复度、按结果里
   最长重复段、按两数接近程度 —— 比看档位总分更容易暴露问题。第 12 轮就是
   档位总分达标而档内分布塌陷。
3. **手工随便试几个。** 第 5 轮是随手输入 `99+999` 试出来的，第 9 轮是手工
   复现错例时推翻了归因，第 10、12 轮同样来自手工试。另外 `eval_llm.py` 用
   temperature 0.85 采样、`eval_math.py` 用贪心，**手工能试出评测器试不出的题**。
4. **"同一个操作的极端情形"往往是独立技能。** 去 1~2 个前导零 98%+，但全部
   塌缩成 0 只有 75%，而去 5 个又是第三回事（§6.2）；判断谁大在 `b/a<0.5` 时
   100%，`b/a>0.95` 时只有 19%。连续量的两端要分别采样、分别统计。
5. **归类错例前先确认归类逻辑本身对。** 曾用"只读竖式计算行"的分类器，把减法
   比较阶段的误读全算成"竖式算错"。也曾用 `'所以' in text` 查残留结论行，
   8000 条里报 3953 例 —— `compare_trace` 的"所以 X 更大"也含这两个字。
   **用解析函数而不是子串。**
6. **补了一档之后，量一下训练数据里实际命中的比例**，并与评测集对照。
   加了采样分支不代表覆盖率够 —— 它会被问法模板、`a>=b` 交换、条件概率
   继续稀释。第 9 轮的 60.3%（以为是 50%）、第 10 轮的 2.8%（以为是 12%）、
   第 12 轮的 0.23%（以为等长档给了 30%）都是同一条链。
   **"我设了 X%"必须插桩实测，不能靠读代码推。**
7. **改动要连带检查被放大的那条路径。** 提高紧凑模板占比后重测序列长度，
   顺手在 12 位上 fuzz，才发现 `10 ** d` 溢出 `UNITS` 这个只测 8 位时不暴露的
   bug。后来在 `--max_digits` 1–12 上又 fuzz 出三处 `randint` 下界越界。
   **把 fuzz 跑到参数两端，而不只是常用值。**
8. **用排除法逼出新机制。** 对每个错例反推"模型把题读成了什么"，凡是现有解释
   套不上的，就是一条没被发现的失败路径。第 8 轮全靠 2 个"解释不通"的例子。
   §6.1 反过来也是：4 个错例精确命中 `10ⁿ−|真值|`，才确定机制是"没交换"
   而非"符号判断错"。
9. **归因之后要找一个反例去否证它。** 验证归因的正确做法不是再找一个符合的
   例子，而是构造一个**按该归因不该出错**的输入。"位数读错源于 tokenizer"
   顺理成章且四轮自洽，但只要问"那带空格为什么也错"就崩了。
10. **顺手查一下词表里到底有什么。** "BPE 两位一组合并"只对 `00 11 22 33 99`
    成立，4~8 压根没有两位 token —— 一条 `d*2 in vocab` 的检查就能看出来，
    却四轮都在凭"BPE 大致会怎么切"推理。
11. **对评测集本身做反向统计，找哪一格是 0。** 按结果符号、结果位数、操作数
    位数关系、写法各切一遍，再把训练集按同样维度切一遍，**两张表并排比倍率**。
    第 10 轮的"负数 0 题"本该在建档时发现，而不是等手工试出来。
12. **补档时先问"机制在哪一侧"。** 第 11 轮按操作数形状补，覆盖的却是答案侧的
    缺陷，效果打了对折。**采样要沿着机制所在的那个变量走，而不是沿着错例
    长什么样走。** §6.1 的机制在"交换要不要触发"这个决策上，所以补数据只是
    让决策点见得更多，未必是结构性修复（见 §7.4）。

## 10. 已知代价

**模型会按固定格式分步演算，而不是直接给答案。** 问"51+29 等于多少"，
它会输出整段竖式。

这是 8 层 / 768 维模型做多位算术的**必要代价** —— 进位链需要中间 token 当
草稿纸，单次前向无论怎么训都做不到（见 §1 根因 4）。

若希望简短算式直接出答案、只在多位时展开竖式，需要在数据里区分两种模式
（如 1–2 位直答、3 位以上展开），属于后续增强项。
